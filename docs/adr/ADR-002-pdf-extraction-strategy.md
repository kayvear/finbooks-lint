# ADR-002: PDF Extraction Strategy — pdfplumber Primary, Claude Vision Fallback

**Status:** Accepted
**Date:** 2026-03-21
**Deciders:** Krish

---

## Context

The validation pipeline needs to read structured data (tables, label-value pairs) from PDF statements generated by fpdf2. Two extraction approaches were evaluated.

Three options considered:

### Option A — pdfplumber only
Use pdfplumber's spatial clustering to extract tables from every page. Fast and deterministic but may fail on visually complex layouts.

### Option B — Claude vision only
Send each page as a base64-encoded PNG to `claude-sonnet-4-6`. Flexible but slower, more expensive, and introduces LLM non-determinism into a mechanical operation.

### Option C — pdfplumber primary, Claude vision fallback (selected)
Run pdfplumber first. If the extraction confidence score drops below a threshold (0.7), switch to Claude vision for that page or section.

---

## Decision

**Adopt Option C.**

`PdfExtractor` (pdfplumber) is the primary path. A per-section `confidence` score (0–1) is computed from parsing success rates. If confidence drops below `0.7`, `VisionExtractor` (Claude vision) is invoked.

Both extractors output the same `ExtractedStatement` / `ExtractedSection` / `ExtractedField` shape so the comparison layer is extractor-agnostic.

---

## Rationale

### Why pdfplumber as primary?
- The PDFs are generated by our own code (fpdf2 with known table structure) — pdfplumber's spatial clustering works reliably on bordered fpdf2 tables
- Zero API cost, no network latency, deterministic
- Runs entirely offline — no dependency on Anthropic API availability for the primary path

### Why Claude vision as fallback?
- Edge cases exist: TOTAL rows with white-on-dark backgrounds may extract as empty; tables spanning page breaks may misalign
- Vision models handle layout ambiguity far better than spatial heuristics
- The fallback is rare — most pages will extract cleanly with pdfplumber

### Why not vision only?
- Mechanical table reading is not a reasoning task — using an LLM for it adds cost and latency for no intelligence gain
- Extraction results can vary across model versions, making validation non-deterministic
- PDF → parquet comparison is an inner loop (one API call per page per customer) — cost scales badly at 1,000 customers

---

## Confidence Scoring

Each `ExtractedField` carries a `confidence` value (0–1):
- `1.0` — cell parsed successfully as a number or non-empty string
- `0.5` — cell was empty or ambiguous
- Vision model's self-reported `confidence` propagated to all cells on that page

Section confidence = minimum across all cells. Statement confidence = minimum across all sections.

Fallback threshold: `0.7` (configurable).

---

## Consequences

### Positive
- Fast and free for the majority of PDFs
- Graceful degradation — layout issues don't cause silent data loss
- Extractor-agnostic downstream (comparison layer doesn't know or care which extractor ran)

### Negative / Trade-offs
- Two code paths to maintain
- Vision fallback requires `ANTHROPIC_API_KEY` and network access
- The `confidence` heuristic is imperfect — a PDF could score 0.9 but still have subtle extraction errors

### Future consideration
If the PDF layout changes significantly in Phase 4 (new asset classes, multi-currency), revisit whether pdfplumber remains reliable or vision should become primary.

## Dependencies

| Library | Role | Note |
|---|---|---|
| `pdfplumber` | Primary text/table extraction | Works well with fpdf2 bordered tables |
| `pypdfium2` | PDF → PNG rendering for vision path | Chosen over `pdf2image` — no system poppler required |
| `anthropic` SDK | Vision API calls | Already a transitive dependency via `claude-agent-sdk` |
